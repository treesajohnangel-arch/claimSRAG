## Details

### D-001 — PostgreSQL + pgvector
Relational data and vectors live in one database, so tenant and version filters can be applied in the same store
that holds the embeddings. No separate vector database is introduced.

### D-002 — PostgreSQL full-text search for keyword retrieval
Keyword retrieval starts with PostgreSQL's built-in full-text search. Elasticsearch/OpenSearch are not introduced.

### D-003 — Hybrid retrieval is mandatory
Policy questions mix exact terms (clause names, defined terms, numbers) with paraphrased intent, so retrieval
combines vector and keyword search. See [ARCHITECTURE.md](ARCHITECTURE.md) §5.

### D-004 — Reranking in the target retrieval architecture
Merged candidates are reranked before they form the evidence set. The reranker is configurable, and the model choice
is made in Phase 7.

### D-005 — Local/private LLM first
The first deployment uses a local LLM through Ollama, so policy content stays within the deployment.

### D-006 — Replaceable LLM provider
LLM access goes through a provider boundary, so future cloud LLMs can be added without changing the answering
pipeline.

### D-007 — V1 users are insurance-company employees
V1 roles are `COMPANY_ADMIN` and `STAFF`. Policyholders and other external users are not V1 users.

### D-008 — No bill auditing in V1
V1 answers questions about policies. It does not audit claim bills or invoices. The "Audit API" in the architecture
refers to audit records, not bill auditing.

### D-009 — Policy Schedule in a later phase
Policy Schedule is Phase 13. Its scope is specified when that phase starts.

### D-010 — Original insurer PDFs are the source of truth
Answers and citations trace back to the original PDFs. Derived data (extracted text, chunks, vectors) can be
regenerated from them.

### D-011 — Not naive fixed-size chunking
Chunking follows policy structure (sections, clauses, tables). See Phase 4.

### D-012 — Clause/page/version provenance
Every piece of evidence keeps its clause, page and policy version, so answers trace back as
Answer → chunk → clause → policy version → original PDF → page.

### D-013 — Company = tenant
In V1, a company is the tenant: an insurance company's isolated workspace. Each user belongs to exactly one company
through `users.company_id`, a NOT NULL foreign key to `companies.id`. Tenant-owned tables use `company_id` as their
tenant key; there is no separate `tenant_id`. Deleting a company that still has users is refused (`ON DELETE
RESTRICT`), so users are never orphaned or silently deleted. Users from different companies may share an email
address. Introduced in Phase 1.1. This is the data foundation only. Authentication and tenant resolution from the
authenticated server-side context come in later Phase 1 tasks, and a client-supplied `company_id` is never an
authorization mechanism (see [ARCHITECTURE.md](ARCHITECTURE.md) §2).

### D-014 — Alembic migrations in SQL, no ORM
- **Tooling:** schema changes are Alembic revisions under `backend/migrations/versions/`, written as explicit SQL
  (`op.execute`), with named constraints.
- **No ORM:** SQLAlchemy is present only because Alembic requires it, and is used only as Core (the migration
  engine). Autogenerate is not used.
- **Driver:** psycopg 3.
- **Allowed values** are `text` columns with CHECK constraints rather than PostgreSQL enum types, which are harder
  to change.
- **Why:** the database enforces integrity itself (keys, uniqueness, allowed values), and every schema change is
  reviewable as SQL and reproducible from an empty database.
- Introduced in Phase 1.1.

### D-015 — Argon2id password hashing
- **Algorithm:** Argon2id, the winner of the Password Hashing Competition and OWASP's first recommendation for
  password storage. It is memory-hard, which makes GPU and ASIC cracking expensive.
- **Library:** `argon2-cffi`, the maintained Python binding to the reference implementation. It is small, with no
  framework attached; `pwdlib` would only wrap it.
- **Configuration:** `app/passwords.py` pins `argon2.profiles.RFC_9106_LOW_MEMORY` (t=3, m=64 MiB, p=4, 16-byte
  salt, 32-byte hash) explicitly, so a library upgrade cannot change the parameters silently. Hashes are
  self-describing PHC strings. The parameters are code constants, not environment settings, because changing them
  is a reviewed code change.
- **Deferred:**
  - re-hashing old hashes after a parameter change (`check_needs_rehash`);
  - a password policy (length, breach checks);
  - pepper / KMS;
  - per-environment tuning.
- Introduced in Phase 1.2.

### D-016 — Company-scoped login credentials
- **Decision:** credentials are `(company slug, email, password)`.
- **Why:** email is unique only within a company (D-013), so email alone can match accounts in several tenants, and
  a plain lookup could authenticate into the wrong one.
- **How:** the slug selects exactly one candidate account, and the password must verify against it.
- **Safety:** the slug is only a selector, not an authorization claim. The authenticated identity's `company_id`
  always comes from the database row. Later login UIs or URLs must supply the company, for example as a company
  field or subdomain.
- **Alternative rejected:** email-only login that checks every account sharing the email. It is ambiguous when one
  person uses the same password in two companies, and its cost grows with the number of accounts.
- Chosen by the user. Introduced in Phase 1.2.

### D-017 — JWT access tokens, RS256
- **Decision:** after `authenticate()` succeeds, the session is a short-lived JWT access token.
  `app/tokens.py` issues it from the `AuthenticatedUser` and verifies it back into a `TokenIdentity`.
- **Why JWT access tokens:**
  - Verification is stateless: no session table, cache or Redis (see the infrastructure rule in
    [CLAUDE.md](../CLAUDE.md)).
  - A bearer token suits the planned React frontend calling the API.
  - The format is standard, and a maintained library implements it.
  - The cost is that a token cannot be revoked before it expires, so its lifetime is short.
- **Why RS256:**
  - It is asymmetric, so only the signer holds the private key. Anything that only verifies tokens needs only the
    public key, and cannot mint tokens.
  - It is the most widely supported asymmetric JWT algorithm.
  - **Rejected:** HS256, whose shared secret lets every verifier mint tokens. EdDSA, which is smaller and faster,
    but there is no concrete need and its support is less universal.
- **Algorithm pinning:** `ALGORITHM = "RS256"` is a code constant. It is the only algorithm passed to verification,
  so the token header cannot choose it. It is deliberately not an environment setting, so a misconfiguration cannot
  select `none` or HS256 either. Changing it is a reviewed code change, as with D-015.
- **Library:** PyJWT with its `crypto` extra (`cryptography`). It is maintained, small, and not an authentication
  framework. Signing and verification are never implemented by hand.
- **Keys:**
  - **Format:** PEM text in `JWT_PRIVATE_KEY` (a `SecretStr`, redacted from logs) and `JWT_PUBLIC_KEY`, from the
    environment or `backend/.env`.
  - **Validated when the settings load:** both or neither are set; the private key is unencrypted RSA of at least
    2048 bits; the public key matches it.
  - **Production** refuses to start without them.
  - **Development** keys are generated locally with `openssl` straight into the git-ignored `backend/.env` (procedure
    in CLAUDE.md, "Access-token keys"). No key is ever committed. There is no symmetric fallback and no key-management
    service.
- **Claims:**
  - Exactly `sub` (user id), `company_id`, `role`, `iat`, `exp` and `jti` (a random UUID4), taken only from the
    `AuthenticatedUser`.
  - No password, hash, email, name, status or company slug.
  - Verification requires every claim and checks its type strictly.
- **Lifetime:** 15 minutes by default. `ACCESS_TOKEN_LIFETIME_MINUTES` accepts 1–60 in every environment.
- **Deferred:**
  - refresh tokens;
  - logout and revocation (no blacklist or token store);
  - key rotation (`kid`);
  - `iss`/`aud` claims (there is one issuer and one audience today);
  - re-checking user status, company status or role on each request (later authorization work);
  - passing the keys to the Compose backend container (with the HTTP authentication boundary).
- Introduced in Phase 1.3.

### D-018 — Static RBAC with default deny
- **Decision:** `app/rbac.py` holds the only role-to-permission mapping. It is an immutable mapping from the two
  existing roles to sets of `Permission` members, and code asks `require_permission(identity, permission)`. There
  are no role comparisons anywhere else.
- **Roles:** only `COMPANY_ADMIN` and `STAFF` (D-007, Phase 1.1). No new role.
- **Vocabulary:** `resource:action` or `resource:subresource:action`, one name per capability:
  `company:read`, `company:user:read`, `company:user:manage`, `policy:read`, `policy:manage`, `search:use`,
  `chat:use`.
  - `COMPANY_ADMIN` has all seven.
  - `STAFF` has `policy:read`, `search:use` and `chat:use`.
  - Each role is listed in full, with no inheritance and no admin wildcard.
  - No endpoint uses these permissions yet. They name the V1 capabilities: company/user administration, policy
    management (Phase 2), search (Phase 6) and chat (Phase 8). None was found unnecessary.
- **Input:** a `TokenIdentity` only. That is the identity `decode_access_token()` produces from a verified token
  (D-017). A role, permission or `company_id` from request data is never an input.
- **Default deny, fail closed:** each of these gets no permissions:
  - an unknown or missing role;
  - a role missing from the mapping, or mapped to a malformed value;
  - an unknown or empty permission;
  - a plain string instead of a `Permission` member;
  - any object that is not a `TokenIdentity`.

  Nothing falls back to `STAFF` or `COMPANY_ADMIN`.
- **401 vs 403:**
  - An authentication failure (`AuthenticationError`, `AccessTokenError`) is HTTP 401.
  - `AuthorizationError` ("Permission denied") means a valid identity without the permission, and is HTTP 403.
  - The two are distinct exception classes, and neither carries detail.
- **Why static and in code, not database-backed:**
  - Two fixed roles and seven permissions fit in a few readable lines, and a change to them is a reviewed code
    change, with tests that pin the matrix.
  - Permission, role or ACL tables would add schema, queries per request and a way to misconfigure access at
    runtime, for flexibility V1 does not need (no custom roles).
  - Revisit if per-company custom roles are ever required.
- **Why no framework:** Casbin, Oso or a policy engine would add a dependency and a policy language for a
  two-role lookup.
- **Not tenant isolation:** RBAC never looks at `company_id`. Whether a resource belongs to the identity's company is
  tenant authorization (Phase 1.5).
- Introduced in Phase 1.4.

### D-019 — The verified token is the only tenant source
- **Decision:** a request's tenant is `TokenIdentity.company_id`, the company id inside a verified access token
  (D-017).
  - `app/tenancy.py` `resolve_tenant(identity)` turns it into a `TenantIdentity(company_id)`.
  - The FastAPI dependency `app/api/tenancy.py` `current_tenant` takes the identity only from `current_identity`
    (D-018's 401 boundary).
  - There is no second token validation and no header access.
- **Why the token, not the database:** the company id was copied from the user's database row at login
  (`authenticate()`, D-016) and is covered by the token signature. A per-request lookup would add a query without
  adding trust. The cost is staleness: a user who moves company keeps the old tenant until the token expires (at
  most 15 minutes by default), and users do not change company in V1.
- **Client values are never authoritative:**
  - A `company_id` in the path, query string, body, a header or a cookie is never an input to tenant resolution.
  - It is ignored, not compared or used as a fallback.
  - A forged company id in a token fails the signature check (401).
- **Why a `TenantIdentity` type rather than a bare UUID:** Phase 1.6 data access can require one, so a company id
  that did not come from verified authentication cannot be passed in by mistake. It holds only `company_id`.
- **Fail closed:** anything but a `TokenIdentity` with a real, non-nil `UUID` company id raises
  `TenantResolutionError`. There is no default, first, nil, global or client-supplied fallback. Over HTTP this is a
  401 with the generic invalid-token response, because only a token the service never issues can reach it.
- **Separation:**
  - Tenant resolution answers *which company* the request acts for.
  - RBAC (D-018) answers *what the role may do*.
  - Resource authorization and tenant-scoped data access answer *whether this resource belongs to the tenant*.
    They are not implemented here: that is Phase 1.6 and later.
  - In particular, this is not a check that a requested company id equals the token's.
- **Single source:** `AuthenticatedUser.company_id` is the login-time value that token issuance copies. No other
  component supplies a request tenant.
- Introduced in Phase 1.5.

### D-020 — Tenant-aware database access in the application
- **Decision:** queries on tenant-owned data go through `app/tenant_db.py` `TenantDatabase(conn, tenant)`.
  - `conn` is a psycopg connection, the pattern `authenticate()` already uses: no ORM (D-014) and no new
    abstraction framework.
  - `tenant` is the `TenantIdentity` from `resolve_tenant()` / `current_tenant` (D-019).
- **Tenant source:** the object stores the `TenantIdentity`, and every query binds `TenantIdentity.company_id` as
  the `%(company_id)s` parameter. It is bound after any other parameters, so nothing can replace it.
- **No caller-selected tenant:**
  - No method takes a company id: `list_users()`, `get_user(user_id)`.
  - The object is immutable and exposes no raw `execute`, so callers cannot write unscoped SQL through it.
  - A bare connection is not a tenant scope.
- **Fail closed:** anything but a valid `TenantIdentity` (None, a UUID, a string, a `TokenIdentity`, a nil or
  malformed company id) is refused before any query. There is no default, first, nil, NULL or caller-supplied tenant.
  As defence in depth, a returned row outside the tenant raises instead of being returned.
- **No role bypass:** the layer has no role input, so `COMPANY_ADMIN` is scoped exactly like `STAFF`. There is no
  super-admin or cross-company access.
- **SQL:** literal statements with bound parameters only. Tenant reads never select `password_hash`.
- **Scope:**
  - `users` is the only tenant-owned table today. `list_users` and `get_user` exist to establish and test the
    boundary; they are not a user-management API.
  - Future tenant-owned tables (policies, documents, chunks and so on) add their queries as `TenantDatabase` methods
    with the same `company_id = %(company_id)s` rule.
  - Pre-authentication login (`authenticate()`, D-016) is the one intended exception: no tenant exists yet, and it is
    scoped by company slug instead.
- **Why application-level enforcement, and why no PostgreSQL row-level security (RLS) yet:**
  - The application uses one database role, and there are no business tables or production queries yet.
  - A single, tested access boundary is the smallest change that enforces the rule now.
  - RLS (`SET LOCAL app.company_id` plus policies) would be a second mechanism, needing per-transaction setup and
    role changes. It stays a hardening option for Phase 14.
- **Not decided here:** resource-ownership rules beyond the tenant, and API-level authorization of routes (Phase 1.7).
- Introduced in Phase 1.6.

### D-021 — API authorization: declared permissions, verified role
- **Decision:** a protected API route declares its permission with
  `Depends(permission_required(Permission.X))` (D-018).
  - That dependency authenticates through `current_identity` (401) and checks
    `TokenIdentity.role` against `ROLE_PERMISSIONS` (403).
  - A route that also reads tenant data adds `current_tenant` (D-019) and `TenantDatabase` (D-020).
  - Each piece keeps its own job; the route composes them.
- **Permissions come from the verified `TokenIdentity.role`.** A role, permission list or `company_id` in the path,
  query string, body, headers or cookies is never authoritative, for either the decision or the tenant.
- **Fail closed:**
  - **401:** missing or invalid authentication, and also a validly signed token with an unknown role, because
    token validation rejects it.
  - **403:** an authenticated role that is not mapped, or a permission granted to no role.
  - **Rejected at route definition:** a value that is not a `Permission` (`TypeError`).
- **Permissions cannot be forgotten.** `create_app()` checks every API route it registers. A route outside
  `PUBLIC_PATHS` (`/`, `/health`) that declares no permission makes the app refuse to start
  (`routes_missing_permission`). Authentication alone, or a tenant alone, is not a declaration. Adding a public route
  is an explicit change to `PUBLIC_PATHS`.
  - Chosen over a custom router class or decorator: it needs no new routing abstraction, and it finds the
    declaration wherever FastAPI allows one (route, parameter, router, `include_router`).
- **Service-level checks are 403 too.** `require_permission()` raising `AuthorizationError` inside a request is
  mapped to the same generic 403 by the central error handlers in `app/errors.py`. Before Phase 1.7 it became a 500
  with a logged traceback: still a denial, but the wrong status.
- **Separate responsibilities:** RBAC does not query the database and knows nothing of tenants. Authorization never
  widens the tenant: COMPANY_ADMIN is scoped to its own company, and there is no super-admin.
- **The permission matrix is unchanged (D-018).**
- **Not decided here:** resource ownership (may this user use *this* policy or document), which comes with the
  business routes.
- Introduced in Phase 1.7. The guard was tightened in Phase 1.8 (D-022); Phase 1.9 added the permission-first rule (D-023).

### D-022 — Fail-closed route guard and pinned boundary rules
- **Why:** Phase 1.8 found two blind spots in the D-021 guard.
  - It exempted `/` and `/health` by path for every method, so an unprotected `POST /health` or `DELETE /` passed.
  - It skipped every non-API route, so a plain Starlette route, a websocket or a mounted application passed.

  No such route existed, but the guard exists precisely to catch that mistake.
- **Decision on the guard:**
  - A public path is exempt only for GET/HEAD.
  - Apart from FastAPI's own documentation pages (`/openapi.json`, `/docs`, `/docs/oauth2-redirect`, `/redoc`), any
    route that cannot carry `permission_required` is reported, and `create_app()` refuses to start.
  - Adding a public route, a websocket or a mounted app now needs its own security decision.
- **Decision on the boundary's single-source rules,** each pinned by a structural test on the application source
  (`tests/unit/test_security_structure.py`, `tests/api/test_route_security.py`):
  - **One verification path:** tokens are verified only by `current_identity`.
  - **One construction site each:** `TokenIdentity` is built only in `app/tokens.py` from a verified token;
    `TenantIdentity` only in `resolve_tenant`, which only `current_tenant` calls.
  - **No request data:** application code reads no query, path, header, cookie or body values. FastAPI's
    `HTTPBearer` reads the credential.
  - **No client tenant/role parameters:** no real route takes a parameter named like a tenant, role or permission
    field.
  - **Scoped SQL:**
    - every statement on a tenant-owned table is tenant-scoped (`company_id = %(company_id)s`);
    - the only exception is the login lookup in `app/auth.py` (company slug);
    - the tenant layer executes SQL only through `_fetch`.
  - **No role comparisons:** no code compares roles; permissions come only from `ROLE_PERMISSIONS`.
  - **No client arguments:** no boundary function accepts a role or company argument.
- **New tenant-owned tables must be added to `TENANT_OWNED_TABLES`** in the structural test, so their SQL is
  checked too.
- **Not a static-analysis framework:** these are a handful of targeted checks, each tied to one security rule.
- Introduced in Phase 1.8.

### D-023 — Authorization before any other route work; final Phase 1 boundary rules
- **Why:** Phase 1.9, the final review of the Phase 1 boundary, found no flaw in the application code. It did find
  developer mistakes that no check would catch:
  - **Permission declared after other work.** FastAPI resolves a route's dependencies in declaration order. If the
    permission check is declared after another dependency (say, one that loads or changes data), that dependency
    runs even for a request that is then denied with 403. The D-021 guard checks only that a permission is declared
    somewhere. A probe confirmed the behaviour: a dependency declared first ran for a denied STAFF request.
    Authentication still came first, and the tenant still came from the token.
  - **Routes added after the guard.** A route added to the module-level `app.main:app` after `create_app()` would
    never pass through the guard, and every existing route test builds a fresh `create_app()`.
  - **Identities copied with new fields.** `model_copy(update=...)` on a `TokenIdentity` or `TenantIdentity`
    creates an identity outside its single construction site, without validation. `model_construct` builds one
    unvalidated.
  - **Environment-dependent behaviour.** A branch on `ENVIRONMENT` or `DEBUG` would never run under the test suite
    (`ENVIRONMENT=test`).
- **Decision:**
  - **Permission first:** a protected route resolves nothing but authentication (`current_identity` and its bearer
    scheme) and tenant resolution (`current_tenant`) before its permission check. Declare the check in
    `dependencies=[...]` on the route or router, or as the first dependency parameter.
  - **Pinned by tests, not the startup guard.** The rule is a structural test over the real application
    (`tests/api/test_route_security.py`). A positive control ties it to FastAPI's actual resolution order. The guard
    (D-021/D-022) is unchanged, since no route with dependencies exists yet and the test runs on the same
    application.
  - **More structural rules** (`tests/unit/test_security_structure.py`, `tests/api/test_route_security.py`):
    - no `model_copy(update=...)` that sets an identity field, and no `model_construct`, anywhere in `app/`;
    - outside `app/config.py`, `ENVIRONMENT` and `DEBUG` are read only in log messages;
    - only `app/auth.py` (the login lookup) reads `password_hash`;
    - the served app has the same routes as `create_app()` and passes the same checks;
    - the public paths are served only by the two dependency-free public endpoints.
- **No production code changed.** Phase 1 is COMPLETE as the protected foundation for Phase 2. Its remaining
  limitations are recorded in [SECURITY.md](SECURITY.md) §10.
- Introduced in Phase 1.9.

### D-024 — Policy and document data model
- **Context:** Phase 2.1 adds the first business tables: Company → Policy → Policy Document. The model is data only;
  there is no API, upload, storage or ingestion yet.
- **Tenant ownership:**
  - Both `policies` and `policy_documents` carry `company_id` (NOT NULL, foreign key to `companies`).
  - **Same-company rule, enforced by the database, not by application checks:**
    - `policies` declares `UNIQUE (company_id, id)`;
    - `policy_documents` references it with the composite foreign key `(company_id, policy_id) → policies
      (company_id, id)`.

    A document therefore cannot be inserted against, or moved to, another company's policy. A policy that has
    documents cannot change company.
  - The application boundary is unchanged: reads go through `TenantDatabase` (D-020), and the tenant comes only
    from the verified token (D-019). There is no RLS.
- **Vocabularies:** CHECK constraints on text columns, as in 0001, mirrored by `StrEnum`s in `app/models.py`. A test
  compares the two.
  - **Insurance type:** `HEALTH`, `MOTOR`, `TRAVEL`, `HOME`.
  - **Policy status:** `ACTIVE`, `INACTIVE`.
  - **Document status:** `UPLOADED` (recorded; nothing has processed or validated it) or `INACTIVE` (withdrawn, kept
    for history).
    - Deliberately **not** `ACTIVE`: in this architecture `ACTIVE` means a *validated* current version (§3 of
      ARCHITECTURE.md, Phase 11). An unprocessed upload must not carry that meaning.
    - Processing states (Phase 3) and the version lifecycle (Phase 11) add their values with their own migrations.
- **Uniqueness:**
  - **Policy number:** unique within a company, `(company_id, policy_number)`, never globally. It is an exact
    match: stored trimmed, with no control characters and no case folding.
  - **Document versions:** unique per `(company_id, policy_id, document_key, version)`.
    - `document_key` (a lower-case slug such as `policy-wording` or `endorsement`) names one logical document of a
      policy; each upload of it is a new row with a new `version` (an integer, 1 or more).
    - A policy can hold several documents, each with any number of versions.
    - The same key and version may appear on other policies.
  - **Storage reference:** unique across **all** companies. Two document rows, and so two tenants, can never point
    at the same stored file.
  - **Checksum (SHA-256, lower-case hex):** not unique. Identical files are legitimate: an unchanged file re-issued
    as a new version, or the same public document held by two companies.
  - **File names:** not unique.
- **Deletes:** `ON DELETE RESTRICT` everywhere, so documents and versions are never removed silently. A company with
  policies, or a policy with documents, cannot be deleted.
- **Storage:**
  - No file content in PostgreSQL (no `bytea`).
  - `storage_reference` is an opaque string (trimmed, no control characters, at most 1024 characters). Its layout
    is decided when storage is built.
  - `original_filename` is display metadata only, never a path. The database rejects `/`, `\` and control
    characters.
  - `content_type` is `application/pdf` only (D-010); `size_bytes` must be more than 0.
- **Not decided here:** effective dates, supersession, freshness, version selection at retrieval (Phase 11),
  processing states (Phase 3), and the storage backend.
- Introduced in Phase 2.1.

### D-025 — A recorded document version is fixed
- **Context:** Phase 2.3 adds the document writes (`TenantDatabase.create_document`, `update_document`,
  `set_document_status`, `delete_document`). The task brief offered a list of "reasonable mutable metadata"
  (document key, version, file name, storage reference, content type, size, checksum, and the policy where safe)
  and asked to update only what the phase genuinely needs.
- **Decision:**
  - **Changeable in place:** `original_filename` (display metadata only, D-024), through `update_document`, and
    `status` (`UPLOADED` / `INACTIVE`), through `set_document_status`.
  - **Fixed once recorded:**
    - the version's identity: `company_id`, `policy_id`, `document_key`, `version`, `id`;
    - its file: `storage_reference`, `content_type`, `size_bytes`, `checksum_sha256`.
  - **Corrections:** a new file, key or version is a new row (`create_document`), and the version number is given
    by the caller, never computed. A mistaken record is set `INACTIVE` or deleted. Deleting removes that one version
    only, never its siblings or its policy, and nothing cascades.
- **Why:**
  - **Invariant 6 and D-024:** policies are versioned, never overwritten, and each upload is a new row. Replacing
    the file behind a recorded version is an overwrite.
  - **Invariant 5, D-010 and D-012:** provenance runs answer → chunk → clause → policy version → original PDF.
    Once later phases attach chunks and citations to a version, changing its file, key or number would make earlier
    evidence point at something else.
  - **Tenant safety:** a document that cannot change policy cannot be moved between policies, or tenants, even by
    a bug. The composite foreign key would still refuse a cross-tenant move, but there is then nothing to refuse.
  - **No need yet:** nothing in Phase 2 needs to relabel a version in place, and deleting or deactivating, then
    re-creating, covers corrections.
- **Consequences:**
  - The Phase 2.4 API offers no PATCH of these fields.
  - Enforcement is in the application: the methods have no such parameters, and the structural rule forbids
    assigning `company_id`, `id` or `policy_id`. It is not a database trigger, so a direct SQL UPDATE is not
    prevented.
  - Revisit with a new decision if a real need to correct a version in place appears, for example before ingestion
    (Phase 3) attaches anything to it.
- Introduced in Phase 2.3.

### D-026 — Policy & document API contract and transaction boundary
- **Context:** Phase 2.4 adds the first business routes (`app/api/policies.py`) over `TenantDatabase`. They are also
  the first application code that opens a database connection.
- **Decision:**
  - **Transaction boundary:**
    - `app/api/database.py` `tenant_database` opens one autocommit connection per request (`app.db.connect`, no
      pool yet) and runs the route inside one `conn.transaction()`.
    - It is declared with `scope="function"`, so the transaction commits after the route returns and **before** the
      response is sent. It rolls back when the route raises, `HTTPException` included.
    - `TenantDatabase` still never commits (D-020).
  - **Order:** the permission is declared first on every route (D-023), so a 401/403 never opens a connection.
  - **Requests:** bodies forbid unknown fields and use strict text and integers. No body carries a company, role,
    permission, id, parent policy or storage reference. Ids come only from the path, and the tenant only from the
    token (D-019).
  - **Responses:** explicit response models without `company_id` or `storage_reference`.
  - **Not found:** another tenant's policy or document gives the same status and body as a missing one. Creating a
    document under such a policy fails in the database (composite foreign key, D-024) and is mapped to the same 404.
  - **Database refusals** map to fixed messages that name at most the client's own field:
    - a duplicate policy number or document version, and deleting a policy that still has documents → 409;
    - a CHECK or data error → 422.

    Anything unmapped propagates to the generic 500. No SQLSTATE, SQL, table, constraint name or value reaches a
    client.
  - **Storage references** are generated by the server: 32 random bytes, URL-safe, carrying no tenant, policy or
    file name. Clients can never send one; they are unique across tenants, so a client-chosen value would reveal
    whether another tenant's exists. No file is stored under them yet.
  - **Document status** has its own `PUT /documents/{id}/status`, separate from the file-name `PATCH`, matching
    the two methods of D-025.
- **Why:**
  - Committing before the response means a client never sees a success for a write that was not committed.
  - One request-scoped transaction leaves nothing partial when a route fails after writing.
  - A connection only after authorization keeps denied requests away from the database.
  - Identical 404s and fixed messages keep other tenants' resources invisible.
- **Not decided here:**
  - connection pooling and production connection management;
  - file upload and the storage backend (whether files are stored under the generated references);
  - audit records;
  - rate limiting.
- Introduced in Phase 2.4.

### D-027 — Chunk size, overlap and chunk ids
- **Context:** Phase 4 adds `app/chunking.py`. Phase 5 embeds and stores its chunks, so the size, overlap and
  identity of a chunk must be fixed first. D-011 rules out naive fixed-size windows.
- **Decision:**
  - **Structure first:** chunks are built from the paragraph blocks Phase 3 separates. A detected heading starts a
    new chunk, and blocks are packed in order.
  - **Size:** one parameter, `max_chars`, default **1500** (allowed 200–8000).
    - It is measured in characters, so there is no tokenizer dependency.
    - 1500 characters is about 250 words or ~375 tokens: most clauses fit whole, and it stays below the 512-token
      input of common local embedding models.
    - A paragraph longer than the maximum is split at sentence ends, then line breaks, then spaces, then a hard
      cut.
  - **Overlap: none.** Chunks end at paragraph or heading boundaries, so overlap would mostly repeat whole
    paragraphs. The same wording would then sit in two chunks, and could be cited twice or inconsistently.
  - **Ids:** `chunk_id` = UUIDv5(fixed namespace, `document_id/version/chunk_index/sha256(text)`).
    - It is deterministic, with no database or randomness.
    - It is stable for the same document version and text.
    - It changes when the text or position changes (for example after a `max_chars` change), so a stored
      embedding can never silently describe different text.
- **Consequences:**
  - Changing the namespace, the default size or the algorithm changes chunk ids, so stored chunks must then be
    rebuilt.
  - Tables and layout are not handled specially yet.
  - Heading detection is a conservative text heuristic.
- Introduced in Phase 4.

### D-028 — Local embedding model and embedding storage
- **Context:** Phase 5 turns Phase 4 chunks into stored vectors for Phase 6. The architecture asks for a
  configurable embedding provider (D-006 for LLMs; D-001 for pgvector), private by default.
- **Decision:**
  - **Provider and model:** `FastEmbedProvider`, BAAI/bge-small-en-v1.5 through fastembed 0.9.1 (ONNX Runtime, CPU).
    - **384 dimensions** and a 512-token input, which suits 1500-character chunks (D-027).
    - **Licences:** MIT for the model, Apache-2.0 for the library.
    - **No PyTorch, no paid API and no extra service.** Ollama was not used: it would add a running service just to
      embed, while this model runs in-process.
  - **Privacy:** the model runs in-process from `backend/.model_cache`. Loading uses `local_files_only` unless a
    download is asked for explicitly, so policy text never leaves the machine and no network is used at run time.
  - **Input:** exactly `chunk.text`. No heading, ids or metadata are added, so the same chunk always gives the
    same input.
  - **Model identity:** each row records `embedding_model` (the exact weights, `Qdrant/bge-small-en-v1.5-onnx-Q`)
    and `embedding_dimension`. A test fails if fastembed ever maps the model name to other weights.
  - **Storage:** `chunk_embeddings`, tenant-owned and immutable, with `vector(384)` fixed. A model with another
    dimension needs a new migration (a new column or table), so vectors of different sizes never mix in one column.
  - **Provenance in the database:** the composite foreign key `(company_id, policy_id, document_id,
    document_version) → policy_documents (company_id, policy_id, id, version)`. `policy_documents` gains that
    unique key. The repeated policy and version columns exist for this key, and for later filtering.
  - **Idempotency:**
    - one row per `(company_id, chunk_id, embedding_model)`; a repeat is recognised (`ON CONFLICT DO NOTHING`) and
      counted as existing;
    - a second, different chunking of the same document and model is refused, so competing embeddings never
      coexist;
    - different models coexist.
  - **Batch:** vectors are validated first (count, dimension, finite) and then stored row by row inside the
    caller's single transaction, so a failure leaves nothing.
  - **Deletion:** RESTRICT, as everywhere. A document with embeddings cannot be deleted (the API answers 409).
- **Consequences:**
  - Each environment downloads the model files once.
  - The Docker image does not contain them.
  - There is no vector index until Phase 6 chooses one.
- Introduced in Phase 5.

### D-029 — Hybrid retrieval and the interim invariant rules
- **Context:** Phase 6 retrieves evidence chunks for a question (D-001, D-002, D-003), before any reranking (Phase
  7, deferred from the accelerated path) or answering (Phase 8). The accelerated path deferred Phases -1, 10 and 11,
  which normally serve invariants 8 and 6.
- **Decision:**
  - **Two paths, both in SQL through `TenantDatabase`:**
    - **Vector:** exact cosine similarity (pgvector `<=>`) between the query embedding and stored embeddings of
      the same model.
    - **Keyword:** PostgreSQL full-text search, `to_tsvector('english', chunk_text) @@ websearch_to_tsquery(...)`,
      ranked by `ts_rank_cd`.

    `chunk_embeddings`, `policy_documents` and `policies` are each filtered on the tenant. The optional
    policy, document and insurance-type filters are bound values that can only narrow the search.
  - **Query embedding:** the query text alone, by the Phase 5 model. No prompt, instruction prefix or metadata is
    added.
  - **Fusion:** Reciprocal Rank Fusion, `Σ 1/(60 + rank)`, deduplicated by chunk. Ties are broken by `chunk_id`.
    - Ranks are fused rather than scores, so cosine similarity and `ts_rank_cd` never need a common scale.
    - Each path contributes `min(max(4·top_k, 20), 200)` candidates, and `top_k` is 1–50 (default 5).
  - **No similarity threshold:** retrieval always returns its best candidates. Judging sufficiency and abstaining is
    Phase 9.
  - **No index and no migration:** exact search is deterministic and fast enough for a tenant's rows at this
    scale. An HNSW or GIN index is a later, measured change.
  - **Invariant 6, interim rule:** only `UPLOADED` documents of `ACTIVE` policies are searched, until Phase 11
    defines validated `ACTIVE` versions.
  - **Invariant 8, interim measurement:** `tests/database/test_retrieval_quality.py`, a fixed corpus and question
    set on the real model and database.
    - The measured baseline is recall@1 = 5/6 and recall@3 = 6/6, enforced as "not worse".
    - An "any word" keyword variant was measured on it at the same 5/6, so it was not adopted.
  - **API:** `POST /search` behind the existing `search:use`, checked first.
    - The responses carry provenance, text and scores, but no company, vector, storage reference or answer.
    - The model loads once per application; if it is unavailable, the response is a generic 503.
- **Consequences:**
  - Full-text search ANDs all query words, so long natural questions often rely on the vector path alone (the one
    known miss in the regression set).
  - Reranking (Phase 7) or a real golden dataset (Phase -1/10) are the measured ways to improve this.
- Introduced in Phase 6.

### D-030 — Local grounded answer engine
- **Context:** Phase 8 turns retrieved evidence into an answer (invariants 3 and 4; D-005, D-006). Reranking
  (Phase 7) is deferred from the accelerated path. Sufficiency, abstention and citations are Phase 9.
- **Decision:**
  - **Provider:** the existing local Ollama server (0.32.6 on the development machine) with `qwen2.5:3b` (3.1B,
    Q4_K_M). It is CPU-friendly and already installed, and there is no paid or external API.
    - The provider boundary is one method, `generate(system, user)` (D-006).
    - It is called with the standard library (`urllib`), so there is no new dependency.
  - **Locality is enforced:**
    - `OLLAMA_BASE_URL` must name a local host (`localhost`, `127.0.0.1`, `::1`, `ollama`,
      `host.docker.internal`), checked when `Settings` loads.
    - Requests ignore environment proxies and refuse redirects.
    - Questions and policy text cannot leave the machine through configuration.
  - **Determinism:** temperature 0, seed 0 and a context of 8,192 tokens are fixed in code. Only the model name,
    timeout and output cap are settings, so a client never chooses a model, provider or prompt.
  - **Evidence:**
    - only the `RetrievalResult` of server-side, tenant-scoped retrieval (Phase 6), in retrieval order, within a
      16,000-character budget (so Ollama never silently truncates the instructions);
    - each passage is fenced by `BEGIN/END EVIDENCE <id> <tag>`, the tag being a SHA-256 prefix over every passage's
      id and text;
    - exact chunk text, with a metadata line built only from structured provenance.
  - **Prompt:** fixed grounding rules:
    - evidence only, no invented terms;
    - a fixed insufficiency sentence when no passage answers;
    - conflicts reported, not resolved;
    - evidence is never instructions;
    - rules never revealed;
    - no citations.

    Rule 2 ("When a passage answers the question, give that answer from it. Only if no passage answers…") was
    chosen by measurement: on a fixed set of 10 real-model cases it passed 9/10, against 8/10 for the plain wording.
    A stricter anti-injection wording was measured too and rejected: no injection gain, and a supported-answer
    regression.
  - **No evidence:** the model is not called, and the insufficiency sentence is returned (`generated: false`).
    This is structural (nothing to ground on), not a sufficiency judgement. There are no thresholds or
    classifiers: those are Phase 9.
  - **API:** `POST /chat` behind the existing `chat:use`, checked first.
    - The body is `{question, top_k ≤ 8, filters}`.
    - The response carries the answer and the evidence the model was shown (not citations).
    - Model failures give a generic 503.
- **Consequences:**
  - Prompt-injection resistance is defence in depth, not a guarantee. With qwen2.5:3b, planted instructions were
    never adopted, but some made the model fall back to "insufficient".
  - Answers repeat exactly within one Ollama server state, but prompt-cache state can flip a borderline answer.
    The real-model tests therefore assert a measured baseline (at least 2 of 3 supported questions) and the safety
    properties strictly.
  - The database transaction stays open while the model generates.
  - The Docker backend reaches no Ollama until Compose is configured for one.
- Introduced in Phase 8.

### D-031 — Evidence sufficiency, abstention and citations
- **Context:** Phase 9 must decide whether the retrieved evidence supports an answer, abstain when it does not,
  report conflicts, and attach traceable citations (invariants 3–5; threats T7, T8, T10). The brief prefers
  deterministic checks, no extra model calls, and no new model, API, dependency or migration.
- **Options considered:**
  - **Score thresholds on retrieval** (similarity or fusion scores): rejected. Relevance is not sufficiency: a
    passage about maternity scores high for a maternity question it does not answer.
  - **A second model call to judge sufficiency:** rejected. It doubles CPU latency, and its judgement would itself
    need verifying.
  - **The model writes citations (pages, documents) in its text:** rejected. Model text is never provenance.
  - **Chosen:** one call that judges and answers together, then deterministic verification by the server.
- **Decision:**
  - **Verdict:** the Phase 8 prompt unchanged (evidence blocks `E1`…`En`, tag, budget, grounding rules 1–5), with
    rule 6 asking for `{"answer", "evidence": ["E1", ...], "status"}`. Ollama constrains the output to that fixed
    schema (`format`); the provider gained an optional `json_schema` argument, set only by server code.
  - **Verification** (`app/grounding.py` `verify`), any failure → ABSTAINED:
    - the verdict parses, and its status is ANSWERED, CONFLICT or INSUFFICIENT;
    - every label is one issued for this prompt, in range, not repeated, and with this prompt's tag if it has one;
    - ANSWERED cites at least one passage, CONFLICT at least two;
    - the answer is non-empty, at most 8,000 characters, and not the insufficiency sentence;
    - no page numbers, numbered references or source lines in the answer; passage labels in it must be cited ones
      and become `[k]` references to the citations;
    - every number in the answer appears in a cited passage or the question.
  - **Citations:** built only from the `RetrievalHit` of each cited label: chunk, document, policy, version, pages
    and section. Never from model or client text.
  - **Abstention:** the fixed Phase 8 sentence and no citations. The reason (`NO_EVIDENCE`, `MODEL_INSUFFICIENT`,
    `MALFORMED_VERDICT`, `UNKNOWN_EVIDENCE`, `NO_SUPPORTING_EVIDENCE`, `INSUFFICIENCY_TEXT`, `CITATION_TEXT`,
    `UNGROUNDED_NUMBER`) is logged, never returned. No evidence still means no model call.
  - **Conflict:** a fixed notice, then what each passage says, with every conflicting passage cited. Never resolved.
  - **API:** `/chat` adds `status` (`ANSWERED`/`CONFLICT`/`ABSTAINED`) and `citations`. All Phase 8 fields keep
    their names and types, and the request body is unchanged.
  - **Rule 6 wording chosen by measurement:** on 11 fixed real-model cases, each run twice with server state
    perturbed in between, status-first wording passed 7/11 (it abstained on 3 supported questions). Answer-first
    wording passed 10/11 in two versions; the adopted one gave identical outcomes in both runs. A version pushing
    harder for CONFLICT once answered a conflict one-sided, and was rejected.
- **Consequences:**
  - Verification is deterministic but not semantic. It proves citations are real shown passages and numbers are
    grounded, not that each passage entails the claim.
  - With qwen2.5:3b, real conflicts end as abstentions (safe), not CONFLICT reports. The CONFLICT path works and is
    tested with a scripted model; a stronger model, or Phase 10 evaluation, can revisit the wording.
  - A number written as a word ("thirty-six") is not checked. Numbers found only in the question are allowed.
  - No migration: citations are computed per request from existing rows and are not stored (audit records are a
    later phase).
- Introduced in Phase 9.

### D-032 — Sign-in endpoint and operator tooling
- **Context:** the frontend needs a real sign-in, but the API had none: `authenticate()` (D-016) and
  `issue_access_token()` (D-017) existed only as services. The startup guard (D-021, D-022) allowed only GET/HEAD on
  `/` and `/health` without a permission. The API also cannot create companies or users, or upload a file, so a
  workspace could not be prepared for an end-to-end run.
- **Decision:**
  - **`POST /auth/login`** (`app/api/auth.py`), body `{company_slug, email, password}` (`extra="forbid"`), response
    `{access_token, token_type, expires_in, user: {full_name, email, role}}`.
    - It is the single entry of `PUBLIC_WRITES`. The guard exempts exactly that path and method; any other method
      on the path, and any other public write, still needs a permission.
    - Its only dependency is `database_connection`: no identity, tenant, tenant database or permission.
    - Every failure (unknown company or user, wrong password, inactive user or company) is the same
      `401 {"detail": "Invalid credentials"}`. Fields default to empty strings, so a missing field fails the same
      way: FastAPI's 422 would otherwise echo the request body, password included.
    - Missing signing keys give a generic 503. Logging is `authenticate()`'s (outcome and user id only).
  - **Operator tooling** (`backend/scripts/workspace.py`, run on the server): `create-company`, `create-user`
    (Argon2id via `app.passwords`; the password is prompted or read from `CLAIMSRAG_USER_PASSWORD`, never a
    command-line argument), `index-document` (stores the PDF write-once under a server-generated reference, then
    records, ingests, chunks and embeds it in the company's `TenantDatabase`, in one transaction) and `sample-pdf`
    (a synthetic, clearly labelled sample wording).
    - It inserts companies and users directly, as the test fixtures do, because `TenantDatabase` has no user writes.
    - It lives outside `app/`, which never imports it (a test pins this), so the served application's structural
      rules are unchanged.
- **Consequences:**
  - The pinned route tests name `/auth/login` explicitly, and new tests pin its shape. No existing assertion was
    removed.
  - Rate limiting and lockout are still absent (Phase 14), and so are refresh and revocation: the token lives
    `ACCESS_TOKEN_LIFETIME_MINUTES` (default 15).
  - Documents still cannot be uploaded over HTTP.
- Introduced in Frontend & Final Integration.
### D-033 — Frontend architecture
- **Context:** the accelerated path ends with a usable application over the existing API, without new
  infrastructure. No frontend existed.
- **Decision:**
  - **Stack:** React 19, Vite 7, TypeScript 5.9 and react-router 7, all pinned. Plain CSS modules on design tokens,
    with no UI kit. IBM Plex Sans and Serif are bundled through `@fontsource`, so no font is fetched from a CDN.
  - **Tests:** Vitest and Testing Library, plus Playwright on the installed Chrome for the real end-to-end run.
  - **API:** one client (`src/api/client.ts`) owns the base URL (`VITE_API_BASE_URL`, default `/api`), the bearer
    header, JSON and error mapping. Errors become fixed user-facing messages: server text is never shown, and
    validation errors name the field only. The dev server forwards `/api` to `CLAIMSRAG_API_URL`, so the backend
    needs no CORS.
  - **Session:** the token, its expiry, the user's display details and the typed company code are kept in
    `sessionStorage` (this tab only), and expire with the token. A 401 ends the session. Sign-out forgets the token
    (the API has no revocation).
  - **Authority:** requests never carry a tenant, role or permission. The role only hides controls; the backend's
    403 is shown when an action is refused.
  - **Evidence presentation:**
    - answers, citations and evidence are rendered as returned;
    - `[k]` becomes a link only when citation k exists;
    - `ABSTAINED` and `CONFLICT` never look like an answer.
- **Consequences:**
  - A token in `sessionStorage` is readable by script on the page, so XSS would expose it. React's escaping, no HTML
    injection, bundled assets and the 15-minute lifetime limit this. An httpOnly cookie would need backend changes
    (D-017 accepts bearer tokens only).
  - A production build must be served behind a proxy that maps `/api` to the backend (Phase 15).
- Introduced in Frontend & Final Integration.

### D-034 — Evaluation & quality specification
- **Context:** invariant 8 asks for every retrieval or generation change to be measured against one golden dataset.
  Phases 6, 8 and 9 measured on small interim sets, and the Phase 7 decision (reranking) needs a stable baseline.
  [EVALUATION.md](EVALUATION.md) §6 left five items to Phase -1: format, counts, thresholds, judging, and K.
- **Decision** ([EVALUATION.md](EVALUATION.md) §6–§18):
  - **Dataset:**
    - `data/evaluation/corpus-v<N>.json` (manifest) and `golden-v<N>.jsonl` (cases), immutable once used;
    - six case types (`ANSWERABLE`, `MULTI_EVIDENCE`, `UNANSWERABLE`, `CONFLICT`, `INJECTION`, `SECURITY`);
    - a v1 minimum of 20 / 5 / 10 / 3 / 5 cases, plus one `SECURITY` case per gate item, over at least two tenants.
  - **Relevance:** a chunk is relevant to an evidence item when its document version matches, its pages overlap,
    and its text contains the item's exact quote (whitespace collapsed).
    - Chunk ids are not used, because they change with chunking.
    - A quote must sit in exactly one chunk, or the run stops and the dataset is revised.
  - **Retrieval:** micro-averaged Recall@K for K = 1, 3, 5, 8, one retrieval per K (candidate pools grow with
    `top_k`); Hit@K, MRR and Precision@K are secondary.
  - **Answers:** a four-label rubric (correct, partially correct, incorrect, unsupported). Automated fact and number
    checks come first; a person reviews every non-correct label and 1 in 5 correct ones. There is no LLM judge in v1.
  - **Citations:** validity, provenance correctness, missing and invented citations are gates (Phase 9 guarantees
    them). Precision, recall (coverage) and support are scores.
  - **Abstention:** outcomes are correct answer, incorrect answer, incorrect abstention, false answer or correct
    abstention, with abstention precision and recall and the false-answer and false-abstention rates.
  - **Conflict:** reported (with each side cited), safe fallback (`ABSTAINED`) or one-sided (`ANSWERED`, a failure),
    so the 3B model's known fallback is visible rather than hidden.
  - **Security:** gates, never averaged. `pytest -m security`, the structural tests, the frontend and end-to-end
    checks, and zero tenant leakage, injection adoption and invented citations in the run itself.
  - **Latency:** `retrieval_ms`, `generation_ms` and client wall time, as p50, p95 and max, with cold start apart.
    The target is TBD.
  - **Protocol:** two runs per case with server state perturbed in between; a case passes only if both runs pass.
    Comparisons hold the dataset version, machine and settings fixed, report counts and per-case changes, and allow
    a trade-off only when it is recorded here.
  - **Thresholds:** absolute for the gates. Interim floors stay as the tests enforce them. Golden-dataset
    thresholds are TBD until the first Phase 10 run, then no regression.
- **Consequences:**
  - Phase 10 builds the runner and golden v1 to this specification. Phase 7 is judged by a before/after run on it.
  - Until Phase 10, the interim measurements of [EVALUATION.md](EVALUATION.md) §17 are the baseline. Recall@5/@8,
    the rubric metrics and latency percentiles are recorded as not yet measured, never estimated.
  - Changing a definition changes the measure: it needs a new decision and a re-measured baseline.
- Introduced in Phase -1.

### D-035 — Company registration, PDF upload, and service errors
- **Context:** the application could not be used end to end from the browser:
  - a new company could only be created on the server (operator tooling, D-032);
  - documents could not be uploaded over HTTP;
  - sign-in answered 500 when the backend was started as the run guide says (from `backend/`, without exporting
    the root `.env`). `backend/.env` held only the JWT keys, so `POSTGRES_PASSWORD` was unset, every connection
    failed (`fe_sendauth: no password supplied`), and `database_connection` let the `OperationalError` become a
    generic 500.
- **Decision:**
  - **Registration:** `POST /auth/register-company` `{company_name, company_slug, admin_full_name, admin_email,
    admin_password}` → 201 `{company: {name, slug}, admin: {full_name, email, role}}`.
    - It is the second entry of `PUBLIC_WRITES`. Its only dependency is `database_transaction`, a new transactional
      connection in `app/api/database.py`, still the only transaction owner.
    - `app/registration.py` validates every field: company name ≤ 200; code `[a-z0-9]+(-[a-z0-9]+)*` ≤ 63; admin
      name; `normalize_email`; and `app.passwords.password_problem`, the new shared policy of 12–256 characters,
      not only spaces.
    - It runs **one** statement:
      `WITH company AS (INSERT INTO companies …) INSERT INTO users (…) SELECT company.id, …, 'COMPANY_ADMIN' FROM company`.
      The company and admin exist together or not at all. The new user's company is never a parameter, and the
      role is a literal.
    - The structural tests pin the statement as the second pre-authentication exception, beside the sign-in lookup.
    - A taken code is a 409. Invalid fields get a 422 naming them, never echoing input. Fields default to "" so
      FastAPI's echoing 422 never fires.
  - **Sign-in:** missing fields are now a 422 naming them (fixed shape, no input), instead of the uniform 401. Every
    authentication failure is still the same 401.
  - **Upload:** `POST /policies/{policy_id}/documents/upload?filename=&document_key=&version=`, behind
    `policy:manage`, with the PDF as the raw `application/pdf` body. This needs no `python-multipart` dependency.
    - The route 404s another tenant's policy, refuses an empty body (422) and a taken version (409), before
      storing anything.
    - `app/indexing.index_document`: `extract_pages` validates the PDF first (`unreadable_pdf` / `no_text`, a 422,
      nothing stored). It then stores the file under `new_storage_reference()` in `DOCUMENT_STORAGE_DIR` (default
      `backend/.document_storage`), records it, ingests, chunks and embeds, all in the request's `TenantDb`
      transaction. The response is 201 with the document and its page and chunk counts.
    - The client's file name is display metadata only (`safe_filename`).
    - Embedding or storage failures give a 503.
    - The operator tooling now calls the same service.
  - **Request size:** `app/request_limits.RequestSizeLimit` (ASGI) receives each body up to `MAX_UPLOAD_BYTES`
    (default 25 MiB) and answers 413 itself when it is exceeded, before any route or authentication. It reads only
    the body's length.
  - **Database outage:** `database_connection` maps `psycopg.OperationalError` at connect time to a generic 503,
    logging the error class and libpq's first line (host, port, reason; never the password). Startup logs a
    warning when `POSTGRES_PASSWORD` is unset.
  - **Settings:** `DOCUMENT_STORAGE_DIR` and `MAX_UPLOAD_BYTES`.
  - **Local fix:** `backend/.env` now carries the database settings. CLAUDE.md's key-generation step now starts
    from `backend/.env.example`.
- **Consequences:**
  - Anyone who can reach the API can register a company (no rate limit, CAPTCHA or approval, Phase 14). A 409
    reveals that a company code exists; codes are what users type to sign in, not secrets.
  - One email may administer several companies (D-013: emails are unique per company).
  - Upload is synchronous: the request returns when the document is searchable (seconds for a typical wording, on
    CPU). No queue was added.
  - FastAPI still reads a body before authentication, now capped by the size limit.
  - A failure after the file is stored leaves an unreferenced file (write-once storage).
  - There is still no user management in the API: further users come from the operator tooling.
- Introduced in the end-to-end demo fix (2026-11-14).

### D-036 — Single-company demo access (no sign-in screen)
- **Context:** the product owner asked for ClaimsRAG to open directly on the dashboard, with no login screen, for a
  single demo company, while keeping the company model, tenant isolation, RBAC and the RAG security intact. Every
  workspace route needs a verified token (D-017–D-021), so the browser still needs a token from somewhere.
- **Decision:**
  - **Settings:** `DEMO_COMPANY_SLUG` and `DEMO_USER_EMAIL`. Off unless both are set; blank means unset; one
    without the other is refused; the code must be a company code. `Settings` refuses them when
    `ENVIRONMENT=production`, so demo access cannot reach production by configuration.
  - **Route:** `POST /auth/demo-session` (no body) → `{access_token, token_type, expires_in, user: {full_name, email,
    role}, company: {name, slug}}`.
    - It is the third entry of `PUBLIC_WRITES`. Its only dependency is `database_connection`; it reads no path,
      query, header, cookie or body. The structural tests pin it like the other public writes.
    - When demo access is off it is a 404 with FastAPI's own body, exactly like a route that does not exist.
    - `app.auth.demo_account` looks the configured user up within the configured company (`c.slug = %(slug)s`,
      the same pre-authentication pattern as sign-in, now the third pinned exception statement). It does not select
      `password_hash`. A missing user, a user of another company, an inactive user or company, or missing signing
      keys is the same 503 "The demo workspace is unavailable"; the reason is logged by user id only.
    - The token is issued by the unchanged `issue_access_token`, from the stored row's company and role.
  - **Unchanged:** `/auth/login` and `/auth/register-company` still exist (the frontend no longer uses them). Tenant
    resolution, RBAC, `TenantDatabase`, retrieval, answering and citations are untouched: every request after the
    demo session is authorised and scoped exactly as with a signed-in token.
  - **Frontend:** the login and registration pages, the route guard's `/login` redirect, sign-out and the
    `sessionStorage` session are removed. A `SessionProvider` fetches the demo session on start and keeps the token
    in memory only (a reload fetches a new one). It renews the token a minute before expiry (or after three quarters
    of a shorter lifetime), retrying every 10 s while the old one is still valid. After a 401 it renews once and
    retries the request once (an upload is not re-sent: the user is asked to try again). `/login` and `/register`
    redirect to `/`. When the session cannot be opened, the app says why (demo access off, workspace unavailable,
    backend unreachable) with a retry, never the server's text. The workspace panel shows the company's name and
    code, the user, the role, and "Demo workspace: opened without sign-in."
- **Consequences:**
  - Anyone who can reach the API while demo access is on acts as the configured user, with that user's role. This is
    acceptable only on a developer machine (ports bound to `127.0.0.1`); it is why production refuses the settings.
  - The demo user's company is the only one reachable from the browser. Other companies still exist and remain
    isolated: their data is reachable only with their own token (sign-in through the API, or the operator tooling).
  - The role shown is the configured user's: configure a STAFF user to demonstrate the read-only experience.
  - D-033's `sessionStorage` token and "401 ends the session" are superseded.
- Introduced in "Remove Login Page and Make ClaimsRAG Open Directly" (2026-11-14).
